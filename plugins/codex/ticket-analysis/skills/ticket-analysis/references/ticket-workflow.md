# 티켓 작업 절차 (Ticket Workflow)

티켓 선언부터 결과 보고까지의 전체 운영 절차. 본 문서가 티켓 워크플로의 **단일 소스**다.

## 1. 프로젝트 선언과 기준 프로젝트

기준이 되는 작업 단위를 **기준 프로젝트**라 한다. 회사 티켓(`IT-\d+`)과 주제 프로젝트(ASCII 슬러그)를 모두 포함한다.

- 선언 문구: `현재 작업이 IT-11111`, `IT-11111 이어서`, `현재 프로젝트가 <ID|제목>`, `<제목> 프로젝트(를) 임포트`, `<ID|제목> 이어서`.
- **해석은 볼트 해석기에 맡긴다** — 스킬이 제목·별칭 매칭을 자체 구현하지 않는다(로직 중복 금지).

    ```bash
    BIV="${BIV_ROOT:-$HOME/obsidian-vault/BIV}"
    python3 -I "$BIV/_tools/index/resolve_project.py" "<질의>"
    ```

    볼트 루트는 `BIV_ROOT` 환경변수가 있으면 그 값, 없으면 `$HOME/obsidian-vault/BIV` 다. 종전의 3순위 폴백(구 홈 별칭 경유)은 **별칭이 제거된 2026-10-20 에 함께 삭제**했다.

- 결과(`match`)별 분기:

    | `match` | `id` | 처리 |
    |---|---|---|
    | `exact` | 확정 | 즉시 기준 프로젝트로 설정 |
    | `partial` | 확정(1위) | **항상 1회 질문** — 1위를 추천으로 제시하고 후보를 함께 보여 준 뒤 확정. 자동 선택하지 않는다 |
    | `ambiguous` | **`null`** | **후보 목록만 제시하고 1회 질문** — 추천을 세우지 않는다(해석기가 1위를 못 정한 상태). 후보에 맞는 것이 없으면 새 프로젝트 생성을 제안 |
    | `none` | `null` | 새 프로젝트 생성을 제안(§2) |

    `partial` 과 `ambiguous` 의 차이는 **`id` 가 채워졌는지**다 — 해석기가 1위를 단독으로 뽑을 수 있으면 `partial`, 동점자가 있어 못 뽑으면 `ambiguous`(`id: null`)다. 따라서 `ambiguous` 에서 임의로 첫 후보를 추천으로 승격하지 않는다.

    `partial` 에서도 반드시 묻는 이유: 1·2위 점수 차가 작아 자동 선택이 안전하지 않다(실측 2026-10-20: "파스토아이 촬영 시작"·"검수패킹 오류 로그" 모두 1위 3점·2위 2점). 엉뚱한 프로젝트에 산출물을 적는 사고는 되돌리기 어렵다.

    실측 경계(2026-10-20, 참고): 1위 3점·단독 → `partial` / 1위 2점 이하에 동점자 → `ambiguous` / 토큰 일치 0 → `none`. 이 임계는 해석기 소유이므로 스킬이 재현하지 않고 `match` 값만 믿는다.

- 스크립트가 없으면(볼트 미설치 기기) 기존 동작으로 폴백한다 — `IT-\d+` 패턴만 인식하고 레코드를 직접 읽는다.
- 프로젝트가 명시되지 않은 요청은 확인을 1회 수행한 후 진행한다.

## 2. 프로젝트 컨텍스트 로드 (임포트 팩)

기준 프로젝트가 정해지면 **팩 생성기를 1회 실행해 그 출력을 컨텍스트로 쓴다.** 레코드를 처음부터 다시 읽지 않는다.

```bash
python3 -I "$BIV/_tools/index/import_pack.py" "<ID>" --budget 3000
```

- 팩 구성: 기준 프로젝트 1줄 → frontmatter → 작업 목표·범위 → 상태 → 미해결 결정 → 진행 기록 최근 5 → 산출물 최근 10 → 최근 세션 워크로그의 미해결·다음 단계 → related → 공동 변경 후보. 첫 줄의 `경로 <소유>/projects/<ID>/` 가 **산출물 라우팅 기준**이다.
- 팩이 비거나 스크립트가 없으면 폴백: 레코드를 직접 읽는다 — **`<ID>/<ID>.md`**.
    - 레코드 파일명은 **폴더 ID와 같다**(옵시디언 폴더 노트) — 그래서 탐지할 이름이 하나다. 볼트가 git 단일 저장소라 기기별 파일명 차이도 없다.
- 레코드가 있으면 `완료 항목` 이후의 `다음 작업`부터 이어서 진행한다. 단, 이어서 진행하는 작업이 체크리스트의 단계를 넘어가는 경우 사용자 컨펌을 받는다.
- 레코드가 없으면 **새 프로젝트 생성을 제안**한다 — `<소유>/projects/<ID>/<ID>.md` (회사 티켓은 `fassto/`, 개인 주제는 `personal/`). ID 는 Jira 키 또는 ASCII 슬러그(`[a-z0-9][a-z0-9-]{2,40}`), 한글 제목은 `title`·`aliases` 에 둔다. `owner` 필수, 주제 프로젝트는 `jira` 생략. 스키마는 `ticket-md-schema.md`.
    - 생성 직후 **인덱스를 1회 재생성**한다: `python3 -I "$BIV/_tools/index/build_projects_index.py" --quiet`
- **`system` 기본값** — 세션 cwd 가 `~/git/fassto/<레포>` 이면 레포 이름을 기본값으로 넣는다.

    | cwd 레포 | `system` 값 |
    |---|---|
    | `fsswms`, `fsswms2` | `fsswms` |
    | `fassto-eye` | `fassto-eye` |
    | `fsshome2` | `homepage` |

    요건 분석에서 다른 시스템이 드러나면 배열에 **추가**한다. 개인 주제 프로젝트는 `[]`. cwd 가 위 패턴이 아니면 추측하지 않고 `[]` 로 두거나 사용자에게 1회 확인한다.

- **이슈 트래커(Jira) 로드는 frontmatter 에 `jira` 키가 있을 때만** 수행한다 — 주제 프로젝트는 Jira 가 없다. 아래 절차는 그 조건에서만 진행한다.
- **`epic` 기입** (`jira` 키가 있을 때만) — Jira 이슈의 parent(에픽)를 확인하고, 그 키의 레코드가 볼트에 **있을 때만** `epic: "[[<소유>/projects/<에픽키>/<에픽키>]]"` 를 기입한다.
    - 레코드가 없으면 **키를 생략**한다. **에픽 노드를 새로 만들지 않는다.**
    - 🚨 **기존 값을 덮어쓰지 않는다** — 이미 `epic` 이 있으면 그대로 둔다. 팩은 `epic` 을 출력하므로(실측 2026-10-20) 보통은 팩으로 확인할 수 있지만, **팩이 레코드보다 오래된 스냅샷일 수 있다**(세션 시작 시 주입된 팩에는 `epic` 이 없었고 그 뒤 볼트가 19건을 채웠다 — 실측). 기입하려면 **레코드 파일을 직접 확인**한 뒤에 한다.
    - 형식은 볼트 기존 값과 동일하게 쓴다 — `epic: "[[fassto/projects/IT-14535/IT-14535]]"`.
- Jira 분석이 필요한 경우(레코드 신규 생성 등) Atlassian MCP 로 다음을 수행한다.
    - 분석 절차:
        1. 해당 티켓의 본문(description) 조회
        2. 해당 티켓의 댓글(comments) 전체 조회 — 댓글에서 합의된 내용이 본문에 미반영되었을 수 있으므로, **댓글의 최신 합의 사항을 본문보다 우선**하여 반영한다.
        3. 해당 티켓에 `relates to`로 연결된 이슈가 있으면 해당 이슈의 본문과 댓글도 함께 조회·분석한다.
        4. 본문 + 댓글 + 연결 이슈를 종합하여 최신 상태 기준으로 분석한다.
    - 생성 항목:
        - 작업 목표/범위 (Jira 분석 기반)
        - 현재까지 완료 항목
        - 다음 작업(미완료 항목)
        - 관련 메뉴/화면/모듈
        - 연결 이슈 요약 (`relates to` 이슈가 있는 경우)
    - 생성 완료 후 §4의 단계별 절차를 따른다.
- 레코드(`<ID>.md`)의 표준 스키마는 `ticket-md-schema.md` 참조. 산출물 저장 경로 규칙은 `artifact-routing.md` 참조.

## 3. 도구 선택 (티켓 시작 시 1회 확인)

| 케이스 | 도구 | 기본 구성 | 비고 |
|---|---|---|---|
| 단순 티켓 (Controller 1~2개, 단일 모듈) | **단일 Claude** (§4 절차 그대로) | Lead 단독 | 팀 spawn 오버헤드 > 이득 |
| 본업 컨벤션 중심·모듈 다수·병렬 가능 | **`deft:agent-teams`** (모두 Claude opus) | BE/FE/QA 3인 (+옵션 designer) | 스킬이 페르소나·단계게이트 내장 |
| 다른 AI 시각·상호 리뷰·토론이 가치 있음 | **`deft:multi-round`** (Claude + Claudex/Codex mix) | 2~4인 회의 (consult/collaborate/debate 등) | 별도 인프라 불요 |
| 한 번에 답 비교만 | **`deft:multi-check`** | Codex + Claude + Gemini | 1회성 fan-out |

> 양방향 토론·페어/Trio·collaborate·signoff 회의는 `deft:multi-round`로 진행한다.

- 도구와 무관한 공통 규칙:
    - 본 §4 단계 게이트(요건분석/영향도/Plan/체크리스트 단계)는 **도구와 무관하게 강제**한다.
    - 레코드 `<ID>.md` 는 **Lead 단독 writer** (표준 구조는 `ticket-md-schema.md`). 팀원은 본인 작업노트만 write.
    - 팀 운영 세부(페르소나·통신·연속성·팀원 이름 규칙)는 `deft:agent-teams` 스킬이 소유한다.

## 4. 단계별 작업 절차 및 승인 규칙

- 티켓이 선언되면, 일반 작업 절차(분석→영향도→변경 제안→승인→적용→검증→보고)를 아래와 같이 확장 적용한다.
- **각 단계 사이에서 사용자 승인 없이 다음 단계로 자동 진행하지 않는다.**

    1. **요건 분석** (일반 절차의 `분석`에 대응)
        - Jira MCP 분석 결과(§2)를 기본 전제로 삼는다.
        - Jira에 없는 추가 요건(Slack 논의, 기획 리뷰 전달사항 등)이 있으면 사용자로부터 수집하여 분석에 포함한다.
        - 방법론: 기능·개선 티켓은 `requirement-refinement.md`, 버그·튜닝 티켓은 `defect-analysis.md`를 먼저 적용 후 합류.
        - 단계 끝에 frontmatter 의 `mentions_screens`·`mentions_tables` 를 갱신한다(본문 2회 이상 언급 기준).
    2. **영향도 확인** (일반 절차의 `영향도 확인`에 대응)
        - `Controller → Service → Mapper XML → SQL` 순서로 영향도를 분석한다.
    3. → **사용자 컨펌**: 요건 분석 + 영향도 확인 결과를 제시하고 승인을 받는다.
    4. **Plan 수립 + 제안** (일반 절차의 `변경 제안`에 대응)
        - Plan 모드에 진입하여 구현 계획을 수립한다. 방법론: `plan-writing.md`.
        - 수립 과정에서 더 나은 방향이나 확인이 필요한 사항이 있으면 사용자에게 질문한다.
        - 계획 확정 후 티켓 `.md` 파일 하단에 `## 작업 계획` 섹션을 추가하고, 작업 순서를 체크리스트 형식으로 기록한다 (문법은 §5).
    5. → **사용자 승인**: Plan 및 제안 내용을 제시하고 승인을 받는다. 승인 시 확정된 Plan·체크리스트를 대화 내에서 사용자에게 바로 안내한다.
    6. **체크리스트 기반 작업 진행** (일반 절차의 `수정 적용` + `검증`에 대응)
        - 체크리스트의 각 단계를 순차적으로 진행한다.
        - 각 단계 완료 시 체크리스트를 갱신(`[O]`)하고, **사용자 컨펌 후** 다음 단계로 진행한다.
    7. **결과 보고** (일반 절차의 `결과 보고`에 대응)
        - 결과 보고 시, 레코드 파일의 갱신 여부와 핵심 변경 사항을 함께 명시한다.
        - frontmatter 의 `related`(연결 프로젝트 위키링크)를 추가하고, 상태가 바뀌었으면 `status`·`status_text`·`updated`(KST `+09:00`)를 갱신한다.

> **frontmatter 편집 규약 (필수)**: 위 갱신은 **frontmatter 만** 수정하고 **본문과 키 순서는 보존**한다. 키 순서는 `ticket-md-schema.md` 의 고정 순서를 따른다 — 그래프·Breadcrumbs 가 키를 읽고, 순서가 흔들리면 diff 가독성도 떨어진다.
> 같은 레코드를 다른 세션과 **동시에 고치지 않는다**(파일 단위 단일 편집자). 볼트는 Git 이고 다른 세션이 커밋 중일 수 있다.
> 새 프로젝트를 만든 직후에는 `python3 -I "$BIV/_tools/index/build_projects_index.py" --quiet` 를 1회 실행한다.

## 5. 체크리스트 문법

- 플래그:
    - `[ ]` 미진행 | `[>]` 진행중 | `[!]` 보류(사유 필수) | `[O]` 완료 | `[X]` 취소(사유 필수)
- 상위 항목 상태는 하위 항목 상태를 종합하여 결정한다:
    - 하위에 `[ ]`가 있으면 → 상위 `[ ]`
    - `[ ]` 없고 `[>]`가 있으면 → 상위 `[>]`
    - `[ ]`, `[>]` 없고 `[!]`가 있으면 → 상위 `[!]`
    - 하위 모두 `[O]` 또는 `[X]` → 상위 `[O]`
- 모든 항목에 넘버링하고, 기본 원칙은 번호 순서대로 순차 진행한다.
- 의존 관계 표기: 병렬 `← (N번과 병렬)` (양쪽 모두 표기), 후속 `← (N번 후속)`

## 6. 티켓 작업 셀프 체크리스트

작업 중·결과 보고 전 스스로 확인한다:

- [ ] 기준 프로젝트를 해석기로 확정했는가? (`partial`·`ambiguous` 면 **1회 질문**을 거쳤는가? `ambiguous` 에서 추천을 임의로 세우지 않았는가?)
- [ ] 임포트 팩을 로드했는가? 레코드(`<소유>/projects/<ID>/<ID>.md`)를 조회/생성하고 완료 항목 이후 작업으로 이어서 진행했는가?
- [ ] 각 단계(요건 분석 → 영향도 → Plan → 체크리스트 각 단계) 전환 시 사용자 컨펌을 받았는가?
- [ ] 결과 보고 시 레코드 업데이트 내용을 함께 기록했는가?
- [ ] frontmatter 갱신(`mentions_*`·`related`·`status`·`updated`)을 **본문·키 순서 보존**으로 했는가?
- [ ] 산출물을 `artifact-routing.md` 규칙대로 라우팅했는가?
