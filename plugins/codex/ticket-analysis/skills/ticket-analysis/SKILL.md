# Ticket Analysis — 티켓 분석·운영 스킬

티켓 선언부터 결과 보고까지, 티켓 작업의 **운영 절차**와 **분석 방법론**의 단일 소스.
구현 자체(코드 수정 기법)는 범위 밖이다 — 각 단계에서 "어떤 순서로, 어떤 승인으로, 어떤 방법으로 분석·계획하는지"를 소유한다.

## 소유권과 우선순위

| 소유자 | 소유 내용 |
|---|---|
| **이 스킬** | 프로젝트 워크플로 전체 — 선언 감지·기준 프로젝트, 컨텍스트 로드(볼트 임포트 팩·이슈 트래커 분석), 단계별 절차·승인 게이트, 체크리스트 문법, 산출물 경로 라우팅, 레코드 스키마, 분석 방법론(요건 정제·Plan 작성·원인 진단) |
| **호스트 지침** (CLAUDE.md / AGENTS.md) | 규칙 우선순위 원칙, 일반(비티켓) 작업 절차, 출력 계약·수정 위치 명시 규칙, 개발 규약·아키텍처 패턴, 본 스킬로의 트리거 문구 |

충돌 시 호스트 지침의 우선순위 원칙(사용자 명시 지시 > 보안 > 그 외)이 최상위다.

## 라우팅 — 언제 무엇을 읽나

| 상황 | 읽을 문서 |
|---|---|
| **프로젝트 선언·이어서 작업** (항상 첫 번째) | `references/ticket-workflow.md` — 선언 해석(볼트 해석기)·임포트 팩 로드·도구 선택·7단계 절차·체크리스트 문법 |
| 산출물 파일을 생성·관리할 때 | `references/artifact-routing.md` — 저장 경로 라우팅·브라우저 리뷰 문서 규칙 |
| 레코드(`<ID>.md`)를 생성·갱신할 때 | `references/ticket-md-schema.md` — frontmatter(키 순서 고정) + 본문 표준 스키마 |
| 기능·개선 티켓의 요건 분석 | `references/requirement-refinement.md` |
| 버그·장애·데이터 정합성·튜닝 티켓 | `references/defect-analysis.md` **먼저** → 원인 확정 후 `requirement-refinement.md`로 합류 |
| 구현 계획(Plan) 수립 진입 | `references/plan-writing.md` |

단계 진입 시점에 해당 문서만 읽는다. 미리 전부 읽지 않는다 — 컨텍스트를 아끼고, 각 단계에서 방법론이 신선하게 적용되도록.

버그 티켓에서 원인 진단이 먼저인 이유: 원인을 모르면 "무엇을 고칠지"(요건)를 정의할 수 없다. 버그 티켓의 원인 규명은 곧 요건 분석의 일부다.

## 공통 원칙 (모든 단계)

1. **단계 게이트 준수** — 각 단계 사이에서 사용자 승인 없이 다음 단계로 자동 진행하지 않는다 (절차는 `ticket-workflow.md` §4).
2. **조사 먼저, 질문은 갭만** — 이슈 트래커 본문·댓글·연결 이슈와 코드베이스를 먼저 조사한다. 조사로 답할 수 있는 것을 사용자에게 묻지 않는다.
3. **질문은 한 번에 하나** — 한 메시지에 여러 주제를 묶어 묻지 않는다. 가능하면 선택지(2~4개)를 함께 제시한다.
4. **사실과 추정을 구분해 표기** — "확인된 사실 / 추정 / 미확인"을 구분한다. 검증 없이 단정하지 않는다.
5. **산출물에 placeholder 금지** — "추후 상세화", "적절히 처리" 같은 표현은 미완성 신호다. 지금 구체화하거나, 미해결 결정사항으로 명시 등록한다.
6. **산출물은 경로 규칙대로** — `artifact-routing.md`의 라우팅을 따른다.

## 안티패턴

- **"단순해 보이니 질문 없이 바로 구현"** — 단순해 보이는 티켓일수록 암묵 가정이 사고를 낸다. 정제는 짧게라도 반드시 거친다.
- **원인 모른 채 수정안 제시** (버그 티켓) — 증상 대응은 재발을 만든다. `defect-analysis.md`의 철칙을 따른다.
- **조사 없이 백지 질문** — 이슈 트래커와 코드를 열어보기 전에 묻는 것. 신뢰를 잃는 지름길.
- **승인 없이 단계 건너뛰기** — 요건→영향도→Plan→진행의 각 게이트는 사용자의 것이다.
- **계획서의 자기 참조** — "Task 2와 유사하게 처리"는 계획이 아니다. 구현자는 순서대로 읽지 않을 수 있다.
